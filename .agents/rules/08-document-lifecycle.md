# 08 — Document Lifecycle

## Purpose

Keep documentation accurate over time without destroying historical context.

## Scope

Creation, update, deprecation, and archival of project documents.

## Applicable tasks

- Updating docs after code changes
- Deprecating obsolete instructions
- Managing changelogs and release notes references
- Retaining research reports and implementation reports for significant governance work

## Normative requirements

1. When user-visible behavior changes, agents MUST update the matching `docs/<command>.md` and the corresponding README **Features** / **Quick Start** / **Usage** (and **How It Works** / **Safety and Limitations** when semantics or limits change) in the same change set when practical.
2. Accepted RFCs are historical records; current contracts belong in living docs (`docs/`, `.agents/rules`, code comments only when necessary).
3. Deprecated instructions MUST record reason and replacement in a migration or maintenance note (see [`docs/maintenance/agents-md-migration.md`](../../docs/maintenance/agents-md-migration.md)).
4. Changelog practice: if `CHANGELOG.md` is introduced later, follow [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and keep Unreleased distinct from released versions. Until a changelog exists, rely on GitHub Release notes generated by the release workflow without fabricating a changelog history.
5. Release packaging currently includes `smtgit.sh`, `shared/`, `docs/`, `README.md`, and `AGENTS.md` (see `docs/release.md`). Adding `RFCs/` or `.agents/rules/` to release archives requires Maintainer approval and a workflow update.
6. Substantial pre-decision investigation MUST be filed as a **Research Report** under [`docs/research/`](../../docs/research/README.md). Research reports answer *what we learned / should consider*; they MUST NOT be used as a substitute for RFC acceptance or for implementation reports. Organize under that directory’s layout: current conclusions as a **flat dated** file (`YYYY-MM-DD-<topic>.md`) listed in the research README, independently valuable stage reports in `supplementary/`, superseded-but-traceable reports in `archive/`. Do not commit temporary notes or duplicate drafts that add no information value.

### Decision-document triad

| Location | Question |
|----------|----------|
| `RFCs/` | What should we do and why? |
| `docs/research/` | What have we learned and what should we consider? |
| `docs/maintenance/reports/` | What did we actually do and what happened? |

### Implementation Report Retention

For significant documentation governance, policy migration, or RFC implementation tasks, the responsible agent MUST produce an implementation report and preserve it in the repository.

Reports MUST:

- Be stored under `docs/maintenance/reports/`.
- Use a descriptive filename containing the completion date and task identifier or subject.
- Summarize the task scope, implementation results, files changed, verification performed, and unresolved issues.
- Distinguish verified facts from assumptions and recommendations.
- Identify decisions that require human Maintainer approval.
- Avoid duplicating the complete contents of the modified documents.

The following tasks require a retained implementation report:

- Initial establishment or restructuring of the documentation governance system.
- Major changes to `AGENTS.md` or agent instruction architecture.
- Implementation of significant governance RFCs.
- Major migrations of documentation rules or policies.

Routine typo fixes, minor wording improvements, and ordinary documentation maintenance do not require separate implementation reports.

Implementation reports are historical records. They MUST NOT be silently rewritten to reflect later decisions or changes. Corrections should be recorded through Git history or an explicitly dated addendum.

A report documents what an agent did; it does not constitute Maintainer approval, RFC acceptance, or authorization to release changes.

Human Maintainers remain responsible for reviewing and approving governance changes.

## Prohibited behavior

1. MUST NOT silently delete obsolete but historically meaningful policy without disposition notes.
2. MUST NOT rewrite old release notes to pretend past behavior differed.
3. MUST NOT invent prior changelog entries.
4. MUST NOT silently rewrite retained implementation reports to match later decisions; use Git history or a dated addendum instead.
5. MUST NOT treat an implementation report as Maintainer approval, RFC acceptance, or release authorization.

## Required workflow

1. Identify documents affected by a change.
2. Update living docs.
3. Leave historical RFCs intact; supersede when needed.
4. Note follow-up packaging/policy impacts for Maintainers.
5. For significant pre-decision research, write or update a report under `docs/research/` (see [`docs/research/README.md`](../../docs/research/README.md)).
6. For significant governance / migration / RFC implementation work, write a retained report under `docs/maintenance/reports/`.

## Verification criteria

- Behavior changes have matching doc updates or an explicit waiver.
- Deprecations are traceable.
- No fabricated release history.
- Research vs RFC vs implementation-report roles are not conflated.
- Required implementation reports exist for significant governance tasks and meet the retention rules above.
